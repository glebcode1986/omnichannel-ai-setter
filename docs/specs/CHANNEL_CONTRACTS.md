# Channel Contracts — v0.1

These contracts are the boundary between channel-neutral core logic and Meta-specific Instagram/WhatsApp implementations. Phase 1 may refine names through an ADR/spec update, but must preserve semantics.

## Core types

```ts
export type ChannelType = "INSTAGRAM" | "WHATSAPP";
export type AiMode = "OFF" | "DRAFT" | "AUTOPILOT";

export type MessageKind =
  | "TEXT"
  | "IMAGE"
  | "VIDEO"
  | "AUDIO"
  | "DOCUMENT"
  | "INTERACTIVE"
  | "TEMPLATE"
  | "REACTION"
  | "UNKNOWN";

export interface ChannelCapabilities {
  text: boolean;
  image: boolean;
  video: boolean;
  audio: boolean;
  document: boolean;
  interactive: boolean;
  templates: boolean;
  reactions: boolean;
  readReceipts: boolean;
  typingIndicator: boolean;
}
```

## Normalized events

All normalized events include:

```ts
interface EventBase {
  workspaceId: string;
  channel: ChannelType;
  channelAccountId: string;
  sourceEventId: string;
  occurredAt: Date;
  rawMeta?: unknown;
}
```

Required variants:

```ts
type NormalizedChannelEvent =
  | InboundMessageEvent
  | OutboundEchoEvent
  | DeliveryStatusEvent
  | ReadStatusEvent
  | ReactionEvent
  | PostbackEvent
  | ConversationPolicyEvent;
```

### InboundMessageEvent

Must provide stable channel identity, external message ID when available, message kind, normalized text/caption, referenced media metadata, reply/quote reference when available and platform timestamp.

### OutboundEchoEvent

Represents messages observed from the platform that may have been sent by our API or by a human using native/platform UI. It must contain enough identifiers for the application layer to classify `AI/AUTOMATION/HUMAN` without adapter-specific logic.

### Status events

Delivery/read events reference a platform message ID and normalized status plus provider metadata/error code where relevant.

## Policy/window model

```ts
export type WindowDecision =
  | { state: "OPEN_FREEFORM"; expiresAt?: Date }
  | { state: "TEMPLATE_ONLY"; expiresAt?: Date }
  | { state: "NOT_ELIGIBLE"; reason: string }
  | { state: "UNKNOWN"; reason: string };
```

Instagram can return `NOT_ELIGIBLE` when no user-initiated conversation exists. WhatsApp can return `TEMPLATE_ONLY` outside the current customer-service window.

## Outbound command

```ts
export interface OutboundMessageCommand {
  workspaceId: string;
  channelAccountId: string;
  conversationId: string;
  recipientExternalId: string;
  operationId: string;       // idempotency/audit identity generated by our app
  replyToExternalMessageId?: string;
  content: OutboundContent;
}
```

`OutboundContent` is a discriminated union. MVP must support text. WhatsApp later adds approved template content; media/interactive support is capability-gated.

## Send result

Adapters must not hide ambiguity behind generic exceptions.

```ts
type SendResult =
  | {
      outcome: "ACCEPTED";
      platformMessageId: string;
      providerRequestId?: string;
    }
  | {
      outcome: "REJECTED";
      retryable: boolean;
      code?: string;
      message: string;
    }
  | {
      outcome: "AMBIGUOUS";
      providerRequestId?: string;
      code?: string;
      message: string;
    };
```

`AMBIGUOUS` means the request may have reached the platform but the system cannot prove whether it was accepted. The application layer moves the delivery to reconciliation/hold and must not blindly retry.

## Adapter interface

```ts
export interface ChannelAdapter {
  readonly channel: ChannelType;

  verifyWebhook(input: RawWebhook): Promise<VerificationResult>;
  normalizeWebhook(input: RawWebhook): Promise<NormalizedChannelEvent[]>;
  getCapabilities(channelAccountId: string): Promise<ChannelCapabilities>;
  evaluateWindow(ctx: ConversationPolicyContext): Promise<WindowDecision>;
  send(command: OutboundMessageCommand): Promise<SendResult>;
}
```

## Adapter invariants

- verification failures never reach normalization/business logic;
- normalization is deterministic for the same webhook payload/version;
- provider-specific error codes are preserved in metadata/logs but converted to normalized outcomes;
- adapter never invokes an LLM;
- adapter never chooses business reply content;
- adapter never implements human-like delays;
- all sends are initiated by application/delivery orchestration after policy gates.

## Testing contract

Each channel adapter must ship fixture-driven tests covering duplicate webhook delivery, malformed/unknown events, text inbound, status events, own outbound echo, human/manual outbound signal where detectable, rejected send, ambiguous send and current channel-window decisions.

## Implementation notes (P1-02)

These notes resolve points the v0.1 text left open; they do not change the semantics above.

- `ChannelType`, `AiMode`, `MessageKind` and `ChannelCapabilities` are defined once in `@omnichannel/domain` and re-exported by `@omnichannel/channel-core`, so domain entities and adapters share one definition.
- **Business Profile scope (DATA_MODEL.md v0.4, Issue #53).** `EventBase` and `OutboundMessageCommand` carry a required `businessProfileId` next to `workspaceId` and `channelAccountId`.
  - Adapters take all three from their trusted account binding, never from the provider payload. The application compares them with the channel account it resolved itself, so an event forged for another Workspace or Business Profile is rejected.
  - Internal scope identifiers (`workspaceId`, `businessProfileId`, `channelAccountId`, plus `conversationId` and `operationId` on commands) follow the domain identifier rules: non-empty, at most 255 characters, no whitespace or control characters. Provider-assigned identifiers keep the looser opaque rule.
  - `ConversationPolicyContext` is unchanged, because window evaluation needs no Business Profile scope.
  - The v0.1 snippets above predate this refinement.
- `RawWebhook` is `{ method, headers (lower-cased names), query, rawBody: Uint8Array, receivedAt }`; signatures are verified against the raw bytes. `VerificationResult` is `VERIFIED | CHALLENGE { responseBody } | REJECTED { reason }`; only `VERIFIED` input may be normalized.
- `ConversationPolicyContext` is `{ workspaceId, channelAccountId, conversationId, participantExternalId, lastInboundAt?, now }`. `WindowDecision` is a platform fact: only `OPEN_FREEFORM` (not yet expired) permits free-form sends, `UNKNOWN` fails closed, and after-window product policy (ADR-014/ADR-016) stays in the application layer.
- Status events: `DeliveryStatusEvent.status` is `SENT | DELIVERED | FAILED` with an optional provider `{ code, message }`; reads are always `ReadStatusEvent` with the read `platformMessageId`.
- `OutboundEchoEvent` carries `platformMessageId`, `recipientExternalId` and, when the platform exposes it, `sendingApplicationId`. Own-echo versus human classification is done by the application from stored send results (ADR-013), never by text.
- `sendDisposition(result)` maps `ACCEPTED -> COMPLETED`, `REJECTED -> RETRY_ALLOWED | FAILED` by `retryable`, and `AMBIGUOUS -> QUARANTINE_NO_RETRY` (ADR-012). The `AMBIGUOUS` variant has no `retryable` field at the type or schema level.
- Normalized payloads are validated with strict Zod schemas (`parseNormalizedChannelEvents`, `parseWindowDecision`, `parseOutboundMessageCommand`, `parseSendResult`). Unknown keys are rejected, so provider fields cannot leak past normalization except inside `rawMeta`. `ContractValidationError` reports paths and issue codes only, never payload values.
